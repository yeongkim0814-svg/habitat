# M0 그래픽 비교 스파이크 (Issue #20, #22)

같은 테스트 장면을 렌더링 스타일 4가지(PSX, TOON, FLAT, PAINT)로 비교한다. **에셋 파일 없이 코드로만 만들었고**(저장소 규칙 2, 예외: 의무실 텐트는 `assets/`의 텍스처가 있으면 읽고 없으면 단색으로 그린다), 반복 구조는 모두 MultiMesh다(D19). 목적은 최종 아트가 아니라 "어느 방향이 이 게임의 분위기와 태블릿 성능에 맞는가"를 판단할 근거를 만드는 것이다. 애니메풍 캐릭터는 만들지 않았고(D12), Fate Trigger는 식생·바위·지형의 분위기 참고로만 생각했다.

## 실행

저장소 루트에서 Godot 4.6.x 이상으로 `res://spikes/m0_look/main.tscn`을 연다.

```sh
godot --path . res://spikes/m0_look/main.tscn
# 스크린샷(가상 화면에서): look = psx|toon|flat|paint, view = street|boundary|field|meadow|overhead|tent|hospital,
#   --hour=0~24, --zone=safe|danger, --torch=off|lamp|shadow(손전등), --hemi=on|off
godot --path . --rendering-driver opengl3 --resolution 1280x720 res://spikes/m0_look/main.tscn -- --shot=paint:meadow:/tmp/paint_meadow.png --hour=10 --zone=safe
# 헤드리스 구조 검사
godot --headless --path . -s tests/m0/run.gd
```

화면 아래 버튼: 윗줄은 스타일 4개(PSX / TOON / FLAT / PAINT)와 시점 7개(거리 / 경계 / 들판 / 초원 / 머리 위 / 의무실 / 병원), 아랫줄은 시각 -3시 / +3시, 구역(안전 ↔ 오염), 손전등(끔 → 켬 → 켬+그림자), 조절, 측정. 시작 룩은 FLAT(D49), 손전등은 켬. **측정**은 스타일 4 × 시점 7을 **손전등 끔·켬·그림자·그림자·켬·끔 순서로**(Issue #42) 90프레임씩 재서 로그에 `M0 look=… view=… torch=off|lamp|shadow mean_ms=… p95_ms=… render_cpu_mean_ms=… render_gpu_mean_ms=… vsync=…` 줄로 남기고, 화면에는 스타일 × 시점마다 `손전등 끔 / 켬 / 그림자` GPU 시간 한 줄(28줄)을 보여 준다. Compatibility 렌더러는 수직동기를 끌 수 없어 프레임 시간(mean_ms, p95_ms)이 주사율 간격에 묶이므로, **렌더러 CPU·GPU 시간(render_cpu_mean_ms, render_gpu_mean_ms)을 스타일 비교의 기준**으로 본다(S1 측정과 같은 방식, GPU 시간이 보고되지 않으면 `?`).

## 조절 패널 (D49)

"조절" 버튼으로 연다. 그래픽을 말로 설명하는 대신 직접 만져서 값을 찾는 도구다(개발용, 최종 게임에는 넣지 않는다).

- 역할 고르기: ◀ ▶로 도로, 건물 벽, 초원 바닥, 바위, 침엽수 등 14개 역할을 넘기고, 색상·채도·명도 슬라이더로 색을 바꾸면 장면에 바로 반영된다.
- 전체 값: 안개 밀도, 주변광 배수, 태양 세기 배수.
- **초기화**: 현재 룩의 조절을 모두 지운다. **저장**: 룩별로 `user://m0_tuning.json`에 저장되고 다음 실행과 스크린샷에도 적용된다. **값 표시**: 바꾼 값을 JSON으로 화면과 로그에 보여 준다. 이 화면을 스크린샷으로 보내면 값을 그대로 전달할 수 있다.
- 시점·구역·룩을 바꿔도 저장하지 않은 조절은 이번 실행 동안 룩별로 유지되고, 저장해야 다음 실행에 남는다. 저장 파일의 안개·주변광·태양 값은 슬라이더 범위로 잘라서 읽는다.
- 측정(벤치마크)에도 저장된 조절 값이 적용되므로, 룩끼리 비교할 때는 먼저 초기화한다.
- 룩의 팔레트 상수(`looks.gd`)는 그대로이고 조절 값이 그 위에 덮인다. 저장 파일이 깨져 있으면 조용히 무시한다.

## 룩 심화 시험 1: FLAT 건물 디테일 (Issue #28)

사용자 평가("FLAT이 단조롭다")에 따라 FLAT의 **벽 머티리얼**(`SHADER_FLAT_WALL`)에 디테일을 셰이더로 그렸다. 메시와 draw call은 늘지 않는다(D19).

- 창 격자(폭 3 m 간격, 층 높이 3.2 m, 창 1.5 × 1.7 m), 1층의 문, 층 구분선, 창 위 그림자, 지붕 윗면 톤 다운.
- 건물은 단위 박스를 건물마다 스케일한 인스턴스라서, `VERTEX × 스케일`이 곧 미터 단위 로컬 좌표다. UV 없이 건물마다 창 개수가 맞게 배치된다.
- 밤(태양 고도가 낮을 때)에는 창의 약 40%가 따뜻한 빛으로 켜진다(`Looks.set_night`, `world.gd`의 `apply_time`).
- 70 m부터 무늬가 사라지기 시작해 150 m에서 없어진다(먼 곳 지글거림 방지).
- 알려진 한계: 건물 모서리의 창 배치는 단순하고, 지붕 형태는 그대로 평평하다. 머리 위 반대편 건물(천장 역할)은 이 셰이더를 쓰지 않는다.
- 확인 방법: 같은 `--hour=10`과 `--hour=20`에서 `--shot=flat:street:…`로 전후를 찍는다. 태블릿에서는 "측정"으로 GPU 시간을 비교한다.

## 룩 심화 시험 2: 건물 형태 다양화와 경계 시점 (Issue #30)

시험 1 결과(사용자): 건물로 읽히고 분위기는 얼추 맞지만 **건물 구조가 모두 같아 거슬리고 건물 모양이 어색하다.** 건물과 초원을 한 화면에서 볼 수 없어 어울림은 판단하지 못했다.

- 건물을 단위 박스 여러 개로 조합한다(`buildings.gd`): 블록, 포디움+탑, ㄱ자, 계단형 후퇴 4종과 옥상 구조물(기계실·계단실). 거리 건물은 여전히 MultiMesh 하나다(D19).
- 건물은 최대 3층(옥상 구조물 제외, 사용자 결정)이고, 박스마다 층 높이(3.0·3.2·3.6 m), 창 간격(2.6~3.8 m), 창 폭, 문 유무를 `INSTANCE_CUSTOM`으로 싣고, FLAT 벽 셰이더가 박스별로 창을 배치한다. 색조는 건물마다 4가지 중 하나에 밝기 변화를 준다. 코니스(옥상 가장자리 띠)를 어둡게 한다.
- **경계** 시점을 추가했다: 거리 건물 사이로 초원이 보인다. 거리 지면을 초원 지면까지 이어 틈을 없앴다.
- 측정(벤치마크)은 시점이 5개가 되어 룩 4 × 시점 5 = 20줄이다.
- 알려진 한계: 건물 모서리의 창 배치는 단순하고, 지붕은 평평하다. 거리 지면은 여전히 한 색이다.

## 룩 심화 시험 3: FLAT 바닥 (Issue #34)

시험 3의 대상은 바닥이다(사용자 선택). 화면에서 가장 넓은 면이 단색이라 장면이 비어 보였다. FLAT 룩의 **스테이지 바닥 메시에만** 바닥 전용 셰이더(`SHADER_FLAT_GROUND`)를 쓴다. 메시와 draw call은 늘지 않는다(D19). 원통 바닥(구간 메시)은 기존 셰이더를 그대로 쓴다.

- 무늬는 스테이지 좌표(미터)에 값 노이즈로 그린다. UV와 텍스처 파일은 쓰지 않는다.
- 거리(시골 마을, D63): 흙길 폭 약 7 m, 바퀴 자국 두 줄, 자갈 얼룩, 길가에서 마당으로 번지는 풀. FLAT의 도로 색을 회색에서 흙색으로 바꿨다(원통 바닥 색도 같이 바뀐다).
- 오염구역 들판: 얼룩진 흙, 갈라짐 선, 외계 서식 환경(D21)을 뜻하는 청회색 얼룩.
- 초원: 풀 얼룩과 흙이 드러난 곳, 밭 한 구획(`Stage.PLOT`, 고랑과 작물 줄, D66·D67). 나무·풀·바위는 밭에 놓이지 않는다.
- 40 m부터 작은 무늬를 줄여 120 m에서 없앤다(먼 곳 지글거림 방지).
- 두 번째 색(길가 풀, 들판 얼룩, 초원의 흙)은 조절 패널 대상이 아니라 `Looks.GROUND_ALT` 상수다. 첫 번째 색은 기존 역할 색(도로, 흙, 초원 바닥)이라 패널로 바뀐다.
- 확인 방법: `--shot=flat:street:…`, `flat:boundary`, `flat:field`, `flat:meadow`로 찍는다. 태블릿에서는 "측정"으로 FLAT의 GPU 시간을 시험 2 측정값(거리 4.44 ms, 경계 4.50 ms, 들판 3.94 ms, 초원 3.92 ms)과 비교한다.

## 룩 심화 시험 4: 야전 텐트 의무실 (Issue #36)

"도형·장난감 같은 느낌"(D85)을 줄이는 방법을 안전구역 의무실 텐트(D68) 한 채로 시험한다. 시점 **의무실**(`--shot=flat:tent:…`)에서 보이고, 측정(스타일 × 시점)에도 들어간다.

| 기법 | 구현(`tent.gd`) |
|---|---|
| 형태의 불완전함 | 천이 기둥 사이와 패널 가운데에서 처지고 주름이 있다. 상자는 조금씩 비뚤게 놓인다 |
| 텍스처 | CC0 텍스처 3장(천, 나무, 판자)을 삼평면 매핑으로 입힌다. UV가 필요 없다 |
| 풍화 | 셰이더 노이즈로 밑단 흙때, 큰 얼룩, 세로 빗물 자국, 약한 채도 감소 |
| 구운 AO | 꼭짓점 색으로 바닥 가까이를 어둡게 하고 조각마다 밝기를 조금씩 흔든다 |
| 땅과의 경계 | 천 밑단에 낮은 흙둔덕, 주변에 풀 덤불(텍스처 없이 셰이더로 잎을 잘라 그림) |
| 소품 | 드럼통(테두리 띠·마개), 틀 두른 표지판(초록 십자), 상자, 간이침대, 모래주머니 |

- **draw call:** 부품을 재질별로 한 메시로 합쳐 텐트 전체가 메시 12개(삼각형 약 5,300개)다. 테스트가 13개 이하를 확인한다.
- **자리:** 거리 서쪽, 가로등 줄(x = -6)과 건물(x = -16) 사이, 문이 거리를 향한다. 테스트가 이 범위를 확인한다.
- **텍스처가 없으면** 같은 셰이더가 단색으로 그리고, 의무실 시점의 화면 글자에 "텍스처 없음(assets 폴더 확인)"을 붙인다. 헤드리스 테스트는 assets 유무에 맞게 텍스처 사용 여부를 확인한다.
- **하늘·땅 주변광**(그늘 속 위·아래 색 차이)은 장면 전체 조명 변경이라 이번에 넣지 않았다. 측정 후 따로 제안한다.
- 측정 비교: 텐트가 화면을 크게 차지하는 의무실 시점의 GPU 시간을 거리 시점과 비교한다. 텍스처 비용만 보려면 `assets` 폴더 이름을 잠시 바꿔 텍스처 없이 한 번 더 잰다.
- **텐트 켬·끔 짝 측정(Issue #38, #40부터는 하늘광 켬·끔으로 바뀜):** 텐트 추가 후 첫 태블릿 측정(120 Hz)에서 텐트가 보이지 않는 시점까지 FLAT GPU 시간이 0.7~0.9 ms 올랐다. 원인이 텐트(숨겨진 시점의 그림자 패스 등)인지 기기 온도·클럭인지 가리려고, 같은 스타일·시점을 텐트 켬과 끔으로 연달아 잰다. 끄면 노드를 숨겨 그림자 패스에서도 빠진다. 한 스타일·시점을 켬 → 끔 → 끔 → 켬 순서로 재고 켬 두 번, 끔 두 번을 각각 평균한다. 측정 중 온도·클럭이 시간에 따라 일정하게 변하면 그 영향이 두 평균에 똑같이 들어가 차이에서 지워진다. GPU 시간이 보고되지 않는 기기에서는 차이 대신 "GPU 시간 없음"을 표시한다. **차이가 0에 가까우면 텐트 비용이 아니라 기기 상태 차이다.** 결과(태블릿, 120 Hz): 24줄 차이의 평균 +0.07 ms, 표준편차 0.31 ms로 텐트 비용은 0과 구별되지 않았다. 한 줄의 흔들림은 ±0.3~0.6 ms다.

### assets 폴더 준비 (태블릿, 처음 한 번)

텍스처는 비공개 저장소 `habitat-assets`에 있다(D14). 이 저장소(`habitat`) 작업 사본 안의 `assets/`에 clone한다. `assets/`는 `.gitignore`에 있어서 이 저장소에 커밋되지 않는다(규칙 2).

1. Termux에서 GitHub CLI 설치와 로그인: `pkg install gh` → `gh auth login` → GitHub.com, HTTPS, "Login with a web browser"를 고르고 화면의 8자리 코드를 브라우저에 입력한다 → `gh auth setup-git`(git이 이 로그인을 쓰게 함).
2. habitat 폴더에서 clone: `cd <habitat 폴더>` → `git clone https://github.com/yeongkim0814-svg/habitat-assets.git assets`
3. Godot 안드로이드 에디터에서 프로젝트를 다시 열면 새 텍스처를 가져온다(처음 한 번 조금 걸림). 의무실 시점에 "텍스처 없음"이 없으면 성공이다.
4. 이후 갱신: `git pull` 그리고 `git -C assets pull`.

토큰을 직접 쓰는 방법도 있다(GitHub 설정 → Developer settings → Fine-grained token, 저장소 `habitat-assets`만, Contents 읽기 전용). 다만 토큰을 비밀번호 칸에 붙여 넣어야 하고 저장하면 평문 파일로 남아서, `gh` 로그인을 기본으로 한다.

## 룩 심화 시험 5: 하늘·땅 주변광과 FLAT 법선 수정 (Issue #40)

### FLAT 법선 버그 수정
FLAT 셰이더 3개(일반, 벽, 바닥)는 화면 미분으로 면 법선을 만든다(`cross(dFdx(VERTEX), dFdy(VERTEX))`). M0는 장면을 SubViewport에 그리는데, Compatibility 렌더러에서는 이 그림이 위아래가 뒤집힌 채 그려져 미분의 부호가 바뀐다. 그래서 **FLAT의 모든 면이 뒤쪽에서 빛을 받는 것처럼 계산되고 있었다**(해를 받는 바닥이 어둡고, 해를 등진 면이 밝음). 구에 FLAT 재질을 입혀 위·아래 색을 재서 확인했다. 수정: 법선이 카메라 쪽을 향하도록 뒤집는다(`dot(NORMAL, VERTEX) > 0`이면 반대로). 이 규칙은 그림이 뒤집혔는지와 상관없이 맞다.
- 영향: FLAT의 밝기와 그림자 방향이 크게 달라진다(바닥이 밝아지고, 나무·건물의 그늘 면이 실제 해 반대편으로 옮겨감). **지금까지 조절 패널로 맞춘 FLAT 값(주변광·태양·색)은 이 버그 위에서 정한 값이라 다시 볼 필요가 있다.**
- PSX·TOON·PAINT는 꼭짓점 법선을 써서 영향이 없다.

### 하늘·땅 주변광 (FLAT만)
- 주변광을 단색에서 하늘(`ProceduralSkyMaterial`)로 바꿨다. 위를 향한 면은 하늘색(`Sun.ambient_color`, 시각에 따라 변함), 아래를 향한 면은 땅 반사색을 받는다.
- 땅 반사색(`ground_bounce`) = 거리 바닥 색 × (바닥에 닿는 직사광 + 약간의 하늘빛). 낮에는 따뜻하고 밤에는 어둡다.
- 오염구역은 장면이 뒤집혀 있으므로 하늘도 축(Z) 둘레로 180° 돌린다.
- 태양 원반은 하늘에 넣지 않는다(`SKY_MODE_LIGHT_ONLY`). 하늘 반사도 끈다. 하늘 계산 해상도는 가장 작게(32) 둔다.
- 스크린샷 비교: `--hemi=on|off`.

### 측정
측정의 켬·끔 짝 대상을 텐트에서 하늘광으로 바꿨다(텐트 비용은 #39 측정에서 0과 구별되지 않음). 순서는 켬·끔·끔·켬 그대로다. 하늘광은 FLAT에만 있으므로 **PSX·TOON·PAINT 줄은 바뀌는 것이 없는 대조군**이고, 그 줄들의 차이가 측정 흔들림의 크기를 보여 준다.

## 룩 심화 시험 6: 오염구역 병원 내부 (Issue #42)

그래픽 대표 장면 3개(D61) 중 "병원 내부"(D60)를 만든다. 조명은 사용자가 고른 B: **바깥 빛(지붕 구멍) + 비상등 + 손전등**. 시점 **병원**(`--shot=flat:hospital:… --zone=danger`)에서 보인다. 병원은 오염구역 장면에 속하지만 M0에서는 구역 버튼과 상관없이 거리 끝 뒤(z = -140)에 늘 있다. 오염구역의 낮은 0시 근처다(D43, 안전구역과 반대 위상).

### 공간 (Claude가 코드로, D88)
- 1층 일부: 복도 폭 3 m, 천장 4 m(D53), 길이 24 m. 동쪽에 진료실(5.75 × 7 m), 복도 끝에 계단실(2층 높이, 꺾인 계단 2단).
- 바닥 비닐 타일과 안내선, 벽 아랫부분 걸레받이 색과 띠, 벗겨진 페인트, 흘러내린 때, 천장 텍스 타일(빠진 칸, 물 얼룩), 꺼진 형광등, 배관, 손잡이 난간, 문(유리창·발판), 쇠사슬 감은 출입문, 침대 2개, 캐비닛, 의자, 커튼, 링거대, 판자로 막은 창, 종이, 무너진 천장 잔해. 표면 무늬는 셰이더가 건물 좌표(미터)로 그린다. **텍스처 파일은 쓰지 않는다**(assets 없이도 같은 모습).
- 부품은 **재질별 + 구역별(복도 3토막, 진료실, 계단실)로 합쳤다**(메시 약 50개). 이 렌더러는 점광원·스포트라이트가 물체를 비출 때마다 그 물체를 한 번 더 그린다. 그래서 건물을 통째로 한 메시로 합치면 비상등 하나가 건물 전체를 다시 그리게 된다. 구역으로 나누면 빛이 닿는 구역만 다시 그린다.

### 빛
- **지붕 구멍(2.4 × 3 m)**: 실제 태양(그림자 있음)이 구멍으로 들어와 바닥이나 벽에 빛 웅덩이를 만든다. 오염구역 태양은 고도가 최대 35°라서 빛이 축 방향으로 비스듬히 들어온다. 그래서 웅덩이는 구멍 바로 아래가 아니라 복도 쪽으로 6~7 m 떨어진 곳에 생기고, 해가 낮아지면 벽으로 올라간다.
  - 천장 텍스 구멍은 지붕 구멍보다 넓다. 같은 크기로 두면 지붕에서 천장판까지 0.7 m를 내려오는 동안 빛이 0.9 m 밀려서 절반이 천장판에 막혔다.
- **빛 기둥**: 구멍에서 빛이 닿는 곳까지 기울어진 상자를 더하기 합성(먼지가 천천히 흐름)으로 그린다. 카메라 가까이에서는 흐려진다.
- **반사광**: 빛이 닿는 곳에 그림자 없는 따뜻한 점광원 하나를 두어 바닥에서 튄 빛을 흉내 낸다.
- **실내 노출**: 어두운 실내에서는 눈이 어둠에 적응해, 구멍으로 들어온 해가 바깥보다 몇 배 밝게 보인다. 병원 시점에서는 태양 세기를 3배로 한다(밖은 보이지 않으므로 노출을 올리는 것과 같다).
- **비상등**: 빨간 등 2개(하나는 깜빡임), 초록 비상구 표시 1개. 그림자 없음.
- **손전등**: 카메라를 따라가는 스포트라이트(범위 22 m, 각도 24°). 눈이 아니라 오른손 위치(오른쪽 25 cm, 아래 22 cm)에 달았다. 빛이 눈과 같은 위치에서 나오면 물체가 만드는 그림자가 모두 그 물체 뒤에 숨어서 그림자가 보이지 않는다.
- **실내 하늘광(D90 열린 점)**: 병원 시점에서는 하늘광을 0.15배로 줄인다. 장면 전체가 환경 하나를 쓰므로, 실제 게임에서는 실내·실외 구역을 나눠 바꿔야 한다.
  - 함께 고친 것: 하늘광을 쓸 때 Godot는 `ambient_light_energy`를 하늘에 적용하지 않는다(색 주변광에만 적용). 그래서 #41 이후 FLAT의 조절 패널 "주변광" 슬라이더가 하늘광에 듣지 않았다. 이제 하늘 재질의 `energy_multiplier`로 슬라이더와 실내 배율을 적용한다. 슬라이더 1(기본)에서 야외 모습은 #41에서 확인한 그대로다.

### 측정
- 짝 측정 대상을 하늘광에서 손전등으로 바꿨다(하늘광 비용은 #41 측정에서 0과 구별되지 않음, D90).
- 순서: 끔 → 켬 → 켬+그림자 → 켬+그림자 → 켬 → 끔. 시간에 대해 대칭이라, 측정 중 온도·클럭이 일정하게 변해도 세 상태의 평균 차이에서 그 영향이 지워진다.
- 화면 줄: `손전등 끔 X / 켬 +a / 그림자 +b ms`. a는 손전등을 켠 비용, b는 거기에 그림자를 더한 비용이다.
- 손전등은 모든 시점에서 켜고 끈다. 야외 시점의 값은 낮에 손전등을 켜 둘 때의 비용이고, 병원 시점이 실제로 쓰는 경우다.
- 보는 법: 병원 시점의 FLAT 끔 값이 실내 장면 자체의 비용, a와 b가 손전등의 비용이다. 120 Hz 예산 약 5 ms(D50) 안인지 본다.

### 하지 않은 것
- 손전등의 게임 규칙(배터리, 생명체를 깨우는 자극 D74)은 제안 단계라 넣지 않았다.
- 2층, 생명체, 소리, 문 열기 같은 상호작용은 없다. 보이는 모습과 비용만 시험한다.

## 회전하는 태양 (D43)

`sun.gd`(순수 함수)가 시각에서 태양 방향·고도·빛 색·하늘색·환경광 색을 계산한다. 태양은 원통 축(Z) 둘레를 돌고, 빛은 축과 각도 α(기본 35°)로 들어온다. 바닥 한 지점은 태양이 반대편에 있을 때 가장 밝으므로 **안전구역이 정오일 때 오염구역은 한밤중**이다(반대 위상).

- 헤드리스 검사(`tests/m0/run.gd`): 안전구역 정오 고도 = α, 해돋이·해넘이 고도 0, 두 구역의 고도가 항상 반대 부호, 각 구역이 하루의 정확히 절반 동안 밝음.
- 화면: 방향광 하나(그림자 켬, 보이는 범위 160 m), 시각·구역 버튼. 구역 버튼은 오염구역 바닥(원통 위쪽, 장면이 뒤집힘)으로 시점을 옮긴다.
- 그림자는 원통 길이(Z) 방향으로 길게 눕는다. 해돋이는 붉고 낮은 각도, 정오는 하얗고 높은 각도, 밤은 환경광만 남는다.
- 단순화: 원통 끝에서의 가림은 무시하고 전체에 평행광을 쓴다. 하루 길이는 물리(실제 외부 태양은 약 63초에 한 바퀴)가 아니라 설정값이다.

## 네 번째 스타일 PAINT (Fate Trigger 참고)

사용자가 제공한 참고 이미지(밝은 하늘, 손그림 느낌의 침엽수·활엽수, 풀 다발, 푸른 그림자, 부드러운 안개)를 **코드만으로 근사**했다. 에셋 파일과 외부 코드는 쓰지 않았다.

| 요소 | 구현 |
|---|---|
| 잎·줄기 명도 | 메시 꼭짓점 색으로 아래는 어둡고 위는 밝은 그라데이션(`nature.gd`) |
| 나무 | 침엽수 = 원뿔 3단, 활엽수 = 겹친 덩어리 3개의 수관(법선을 구형으로 둥글게)과 줄기 |
| 풀 | 날 5장짜리 다발 2,200개, 끝이 노랗고 바람에 흔들림(셰이더) |
| 질감 | 월드 좌표의 값 노이즈 2단(큰 얼룩과 작은 붓질)으로 색을 흔듦 |
| 빛 | 감싸는 조명(wrap), 환경광을 푸르게 해 그림자에 푸른 기 |

이 초원 시점은 다른 세 스타일에서도 같은 장면으로 보인다(모두 MultiMesh: 바위, 침엽수, 수관, 줄기, 풀).

## 이번 단계의 한계

- PAINT는 아직 지면이 과하게 밝고(노출 조정 필요), 바위 모양이 단순하다. TOON·PSX는 새 조명에 맞춰 다시 조정하지 않았다(침엽수가 어둡게 보임).
- 풀은 날이 단순해 가까이서 보면 거칠다. 밀도와 구역 나누기는 태블릿 측정 후 정한다.
- 손으로 그린 텍스처의 밀도는 에셋 없이는 한계가 있다(P4에서 외부 에셋 또는 AI 생성 텍스처, D26·외부 에셋 규칙을 따름).

## 알려진 한계 (M0 첫 PR)

- 스크린샷은 **가상 화면의 소프트웨어 렌더링**이다. 색감과 구성은 볼 수 있지만 프레임 시간은 의미가 없다. 태블릿 프레임 시간은 사용자가 측정 버튼을 눌러 기록해야 한다(미실행).
- 식생의 잎은 단순한 프리즘이라 모양이 거칠다. 최종 아트가 아니라 스타일 비교용이다.
- 머리 위 구역은 원통 길이를 늘려 확인한다(S2의 200 m 원통은 끝이 보인다). 실제 게임의 원통 길이는 미정이다.
- 외곽선(TOON)은 월드 단위 두께라 멀리서는 가늘어 보인다.
